# Pre-T016 adversarial reconciliation architecture review

Separate root architecture/security pass before reconciliation implementation;
not a separate-model/human review. Execution coordination milestone7cdc0c6 at L0.

Required invariants:
- SUBMITTING/UNKNOWN never implies rejected or absent. Reserve remains; no send retry.
- Query by durable client/venue identity through an internal adapter, bind source
  observation to exact request/account/tenant/symbol/side/quantity and current order.
- A query returning no order or an SDK exception is unresolved; absence requires
  explicit corroborated complete account/history/time coverage. No automatic retry.
- Found open order may recover ACKNOWLEDGED but cannot fabricate full-account health.
- Cumulative fill without full immutable fill IDs/prices/fees is known unsettled
  truth. Store it, block new risk and obtain canonical fills; never mark financially
  settled or release remaining reservation based on a bare terminal status.
- Canonical duplicate fills are idempotent, changed-ID bodies are incidents. Fill
  journal and resulting order state commit atomically. Cancellation releases only
  proven remainder after accounted fills and complete terminal reconciliation.
- Known unattributed or fee-insufficient venue fill must not be dropped. Append
  durable raw truth/suspense incident, preserve attribution failure and deny new risk.
- Reconciliation/account safety does not depend on Claude or remote OPA availability.
- One recovered order alone does not prove balances/all orders/reservations healthy.
  Test source is explicitly loopback official-SDK fixture, never L4 venue evidence.

Current implementation boundary: only protective SIMULATION preparation can claim
transport; fixed dummy-auth SDK fixture cannot target Binance or inherit owner keys.
Next increment proves accepted timeout -> query-found recovery with one submitted
order; partial fill/cancel/full-account accounting remains separate required work.
